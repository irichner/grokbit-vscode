# CLAUDE.md — Grokbit (fork of grok-build-vscode)

**Grokbit** — VS Code extension for **xAI's Grok Build CLI**, driven by `grok agent stdio` over the [Agent Client Protocol (ACP)](https://agentclientprotocol.com). Thin client — all session state, MCP servers, subagents, memory, and plan-mode bookkeeping live in the CLI. **Each session renders in its own native editor tab** (`WebviewPanel`, view type `grok.session`); the activity-bar view is a session **launcher** (list + New), not the chat. Fork of `phuryn/grok-build-vscode` (MIT — attribution kept in README/welcome/About). Primary source is now https://github.com/irichner/grokbit-vscode. Published as **`grokbit.grokbit`** (publisher `grokbit`) — a fresh Marketplace listing, distinct from the original `PawelHuryn.grok-vscode-phuryn`; the install scripts remove the old listing on install since the two register the same `grok.*` commands/views and can't coexist. Rebrand covers `package.json` identity (`name`/`publisher`/`author`), display name, activity-bar/Settings/command titles, welcome + About copy; `grok.*` command IDs, setting keys, the `grok.chat` view id, and the AI-persona strings are unchanged.

## Status

See [CHANGELOG.md](CHANGELOG.md) for the current version and full release history (the Marketplace/GitHub-published build can lag the local working tree). The whole test suite is **grok-free** — CI never spawns the binary; grok-dependent probes live separately in `research/*.cjs`. Plan mode is **enabled** and enforced client-side (see `research/plan-mode.md` § Resolution). Smoke-tested end-to-end on Linux, Windows-via-WSL, and the **native Windows build** (`irm https://x.ai/cli/install.ps1 | iex`) — `cli-locator` resolves `grok.cmd`/`grok.exe` and `terminal-manager` uses `shell:true`.

This file is the project map: it describes the **current** architecture, not a per-version log. The full release history lives in [CHANGELOG.md](CHANGELOG.md); feature internals are documented in the dedicated sections below (§ Module map, § Session pool, § History pagination, § ACP surfaces implemented) and in `research/*`.

**Grok CLI compatibility (#22).** `grok agent stdio` had a Windows-only regression — the agent didn't read stdin lines until EOF (which never comes for a live client), so an ACP startup request hung and the session couldn't start (*"Grok exited (code null)"* / *"ACP request timed out: …"*). The hang moved across builds (`initialize` on 0.2.61–0.2.64, then `session/new` on 0.2.67–0.2.70) and was **fixed in 0.2.71** (verified via the session/new probe + the live ACP gate). The extension pins Windows to the supported build via pure guards in [src/cli-locator.ts](src/cli-locator.ts), all **Windows-only** (each early-returns to a no-op off win32): `isStdioBrokenGrokVersion` flags the **bounded broken range 0.2.61–0.2.70** (the fix sits *above* it, so it's a closed range, not open-ended) so `maybePinBrokenCli` pins those builds up to the supported 0.2.72 (the fix landed in 0.2.71 and is now on stable as 0.2.72) before spawning; and `shouldReactivelyDowngrade` is the evidence-driven backstop — on an observed startup failure (`initialize` *or* `session/new`) on a build **above** 0.2.72 it switches to 0.2.72 and retries the spawn once (`downgradeBrokenCli`, loop-guarded by `reactiveDowngradeInFlight`). Windows updates are **no longer paused** (`grokUpdatePolicy` allows normally) now that the fix shipped. The supported build is the single-source-of-truth constant there (`GROK_STDIO_DOWNGRADE_TARGET`); exact versions, diagnosis, and probes in `research/stdio-eof-regression.md`. When a newer Windows-verified build ships — **verify with the session/new probe, not just initialize** — bump the constant and widen the broken range to include the superseded builds.

## Native tabs + session pool

**Each session is its own editor tab** — a `WebviewPanel` (view type `grok.session`) rendering the same `getHtml`/`chat.js` webview; the activity-bar `grok.chat` view is the **launcher** (`getLauncherHtml` + `media/launcher.js`: a windowed, paged Recent list (default 30 days — see § History pagination), dots, New, rename/delete, signed-out/missing-CLI states — full, unwindowed history + search live in the chat history popover). A session is never rendered in two webviews at once. Host state: `pool` (live processes), `panels` (open tabs), and nullable `active` (last-active tab — the target for editor commands; every reader handles undefined, and command entry points open a tab if none). Delivery is the pure `PanelRouter` (`src/panel-router.ts`) with three intents: **`emit(session,…)`** (buffered chat content — always appended to `Session.buffer`, delivered live only while the panel is `ready`; content streamed into a hidden tab is replayed losslessly on reveal), **`postTo(session,…)`** (transient one-panel messages, dropped when not ready BY DESIGN — only request replies and replay-derived ephemera: `modeChanged`, `chips`, voice partials, `grokUpdateStatus`, `initialState`, `sessions` reply, `capabilities` — derived, refreshable state that must never enter `Session.buffer`, since a replayed stale capability list would be wrong after the user adds a skill), and **`broadcast(…)`** (every ready panel + the launcher: `cliUpdating`, `onboarding`, `fontScale`/`showThinking`/`voiceConfigured`, `sessionDot`, sessions-list refreshes). **`ready` lifecycle:** panels use `retainContextWhenHidden:false`, so a hidden webview is torn down and its reveal re-runs chat.js, which re-fires `{type:"ready"}` → mark ready, post per-panel config (`postPanelConfig`), `replayInto` (clear → buffer → derived mode/chips last), and consume `pendingStart` (lazy spawn). **`ready` never spawns; panel creation drives `startSession`** (`newTab`/`openTabForId`); `pendingStart` covers the lazy cases (serializer-restored background tabs, post-CLI-update respawns). Flipping `retainContextWhenHidden` to true silently breaks the replay lifecycle (`ready` wouldn't re-fire) — deliberate dial, don't turn casually. **Tab titles:** the pure `tabTitleFor` (`src/sessions.ts`, ~24-char, "Grokbit New" when unnamed); precedence `customName` → in-memory first prompt → disk displayName; update points: panel creation, first send, `maybeGenerateTitle`, `renameSession`, `carrySessionName` restarts, cold-load/restore. **Open dedupe:** every panel-materializing entry point (launcher row, dropdown row, serializer restore) funnels through the router's shared `opening` set. Each of those entry points also carries the clicked row's own **`backend`** through to the fresh `Session` before `startSession` runs — `openTabForId(id, backend)` (launcher row / history dropdown row) and `restorePanel(panel, id, backend)` (serializer restore) — since a bare session id doesn't say which store/agent it belongs to; a Claude row now resumes a real Claude session and a grok row a grok one (docs/plans/claude-code-backend.md § WP5; before WP5 every resume silently opened a grok tab regardless of the row's backend). **Close semantics (`onPanelClosed`):** dispose the live process but keep on-disk history (reopenable from the launcher with full replay); an empty primer-only session is deleted from disk instead (#24, **grok-only** — gated on `backendSpec(session.backend).quirks.emptyPrimerSweep` via the pure `shouldRecycleEmptySession` in `session-pool.ts`; Claude never receives the hidden primer, so a closed Claude tab, empty or not, always keeps its history); close any diff previews for pending edit approvals; cancel a voice capture the panel owned; re-home `active` by `lastActiveAt`. **Reload persistence:** a `WebviewPanelSerializer` (+ `onWebviewPanel:grok.session` activation event) restores tabs; the webview stashes `{id, backend}` via `setState` on the `session` event — `backend` comes from that event's OWN field (stamped by the host from `session.backend` at emit time), not read back from `state.backend` in the webview, since a mid-session backend flip's fresh `session` event can outrace its own `backendChanged` and would otherwise persist the stale backend; only the visible tab spawns (`spawned grok (pid …) — N live` / `spawned claude (pid …) — N live` in the Output channel is the observable), background tabs spawn on first reveal — `session.backend` rides along on the same in-memory `Session` object across that lazy-start deferral, so a background Claude tab still respawns Claude on first reveal, not grok. **Status dots** unchanged in spirit (pure `computeDot`: working → needs-you → unread(error?) → none; unread = persisted meta badge set when a turn ends while the tab isn't visible, cleared on open/reveal — survives tab close AND reload). **Process bounding is a soft guard now:** the time/LRU reaper is retired (an open tab is user-owned; never silently killed) — past `MAX_LIVE_SESSIONS` (8) a one-time-per-window warning suggests closing tabs; lazy start is the structural mitigation. **Global flows under N tabs:** `updateGrokCliOnDemand` confirms on busy sessions, broadcasts `cliUpdating`, awaits `disposePool()` (Windows binary lock — still tears down every backend's pool, since it disposes every panel to free the locked grok binary regardless of backend, a known minor over-tear-down in a mixed-backend window that WP5 didn't change), updates, then respawns the active visible tab immediately and marks every other panel `pendingStart` (respawn on reveal — no orphaned dead tabs); **`logout` is per-backend** (`logout(backend)` fronting `logoutGrok`/`logoutClaude`, WP5 — fixes the WP3-flagged inconsistency where a Claude tab's gear-menu "Log out" silently signed the user out of grok instead): `disposePool(backend)` tears down only that backend's live sessions, closes only that backend's panels (`s.backend === backend` filter — a tab on the other backend is untouched), and posts the signed-out onboarding state directly to the **launcher only** (never a fan-out `broadcast`, since every panel of the signed-out backend was just closed and a still-open tab on the OTHER backend must never show the wrong backend's signed-out card); `clearAllSessions` protects **every open panel's** session id (`clearSessions` takes `exceptIds: Set<string>`); `deleteSession` also closes the session's open tab. **Voice is single-owner:** the capture is bound to the session that started it (`voiceOwner`), all voice posts route to it, a second concurrent start from another tab is rejected, and closing the owner tab cancels the capture. The impure `voice-recorder`/`voice-streamer` (ffmpeg spawn + STT fetch/WebSocket) are smoke-tested manually via the `research/voice-*.cjs` probes (`voice-stt-probe`, `voice-e2e-verify`, `voice-stream-probe`, `voice-stream-verify`, `voice-cost-probe`).

**Empty-primer-session cleanup (#24).** Every time a session tab opens it primes a fresh grok session (`ensurePrimed`); if the user never sends a real message that leaves an empty, primer-only session on disk, titled from grok's primer-derived summary ("… Primer v4 Plan Mode …"). Two mechanisms keep those out of history. **(1) Recycle on close (in-memory, bulletproof):** `onPanelClosed` knows a session is primer-only via `hasHistory === false` (the primer is sent through `ensurePrimed`, *not* the `send` path, so it never sets `hasHistory` — and a *resumed* session only gets `hasHistory` when its replay contained a real user message, `userMessageCount > 0`, so reopening a lingering primer-only session doesn't re-arm it as "real"), and on tab close it deletes that session's on-disk dir (`removeSessionFromDisk`), not just its process — abandoned "New session" tabs leave nothing behind, and `buildSessionsMessage` forces a live empty session's display name to "New session" while live (in-memory `!hasHistory`), never grok's primer title (the tab title mirrors this via `bestNameFor`). The delete runs **after the process actually exits** (`disposeSession` returns the client's exit promise; grok re-persists its dir during shutdown, so an eager delete loses the race), retries once for a late flush, and is skipped when the session was renamed (`customName` = keep-intent, mirroring the sweep) or reopened meanwhile. Webview counterpart: a replay whose every turn is suppressed (primer-only) keeps the **welcome screen** up — `appendUserChunk` must not `clearWelcome()` before its primer check, or the tab renders a fully blank pane (the original #24-resume bug; regression-tested in `test/primer-only-restore.dom.test.ts`). **(2) Startup sweep (legacy cleanup, content-confirmed):** `sweepEmptyPrimerSessions` runs once per activation (kicked off from the first successful `startSession`) over the newest `SWEEP_SCAN_LIMIT` by mtime; it skips live + renamed (`customName`) sessions, then reads `chat_history.jsonl` and deletes only if `isEmptyPrimerSession` confirms the session got our primer and **zero real user queries** — so a real session (even one with a primer-contaminated title) or a session we didn't start (no primer) is never touched. **The chat-history content check is authoritative regardless of `num_messages`** — `EMPTY_PRIMER_MAX_MESSAGES` only gates the no-content title-heuristic fallback. An *agentic* primer turn can balloon past that gate (a real captured case: 74 messages — primer + tool/reasoning turns, re-primed on restore — with zero real queries), so gating the content read on the count left those lingering; the count must not veto content. Detection is content-based and agent-agnostic: grok keys the role on `type` (not `role`), wraps prompts in `<user_query>` **but not always** (slash commands like `/imagine` arrive UNWRAPPED — composer especially), and tags injected `<system-reminder>`/context turns `synthetic_reason`; `extractUserQueries` handles all of that, so the same logic works for the `grok-build`/`grok-build-plan` and `cursor` (composer) agents alike (verified against real on-disk sessions of both).

## History pagination

The history popover loads sessions **one page at a time** (`SESSION_PAGE_SIZE = 100`, newest-first) so it stays responsive with thousands of sessions on disk, **merged across both backends** (grok + Claude Code, #WP4) into one list. The cost of the old behavior (read + `JSON.parse` *every* `summary.json` on every open, then render every row) grew linearly and stalled the popover at scale; a naive per-backend list would have doubled that cost, so the pagination/cache/search machinery is backend-agnostic by construction.

**`src/session-store.ts` — the `SessionStore` seam.** Each backend's on-disk layout is wrapped behind one interface (`index(cwd)`/`readEntries(cwd, ids, overrides)`/`remove(cwd, id)`/`removeAll(cwd, exceptIds)`/`readTokenUsage(cwd, id)`), so `sidebar.ts` never branches on layout:

- `GrokSessionStore` — a thin, behaviour-preserving wrapper around the pre-existing pure primitives in `sessions.ts`: `indexSessions({fs, grokHome, cwd})` (one `stat` per session dir, **no reads/parses**, newest-first by `summary.json` **mtime** — the cheap last-activity proxy, since the id is a UUIDv7 whose timestamp is creation, not last activity) and `readSessionEntries({fs, grokHome, cwd, ids, overrides})` (reads + parses `summary.json` for **exactly the given ids**). `listSessions` (index + read-everything) is kept for callers that genuinely need the whole list.
- `ClaudeSessionStore` — new: Claude Code stores one **flat file** per session (`~/.claude/projects/<encoded-cwd>/<uuid>.jsonl`, not a directory), so `index()` stats `*.jsonl` mtimes directly (same last-activity-proxy rationale as grok). The project directory name is every non-alphanumeric character of the cwd replaced with `-`, **preserving case** (`resolveClaudeProjectDir`/`claudeProjectDirName`) — verified on real machines to need a **case-insensitive fallback** on Windows, since the drive-letter case in the encoded name follows whatever exact cwd string a given tool passed at session-creation time (the same user ends up with both a `C--Users-…` and a `c--Users-…` directory for one project). Title derivation never reads a whole `.jsonl` (real sessions run into the megabytes): `deriveClaudeRawTitleSource` reads bounded head/tail byte slices (`ClaudeFsLike.readSlice`) looking for the **last** `type:"ai-title"` record (Claude Code has no `type:"summary"` record — that was the original plan assumption, disproven by inspecting real sessions; `ai-title` is regenerated repeatedly as the conversation grows, so the latest one is the most refined), then the first real user message (skipping `isSidechain` turns, `tool_result` content blocks, and slash-command scaffolding — all of which start with `<`, the same signal grok's own `extractUserQueries` uses), then `fallbackName`'s dated "Untitled" — identical three-tier fallback to a grok session with no `session_summary`. `numMessages` is always 0 (an exact count needs a full parse); the row's "N msg" fragment just omits itself, same as any zero.

**Merge (`buildMergedSessionsPage` in `session-store.ts`, pure).** Both stores' `index()` results are concatenated and sorted by mtime once; pagination and search operate on that single merged, interleaved-by-recency list — a Claude session between two grok ones in real time stays between them in the popover, not grouped by backend. `readEntries` is injected so the caller's cache sits in front of the actual per-backend reads (see below); the merge itself never touches file content beyond the cheap index pass. Extracted specifically so this is unit-testable without `vscode` (`test/session-store.test.ts`), matching the codebase's usual pure-logic/impure-glue split.

**Host orchestration** (`buildSessionsMessage` in `sidebar.ts`, fanned out via `replySessionsList(session,…)` — a dropdown reply to the requesting panel, `postLauncherSessions(…)` — the launcher's own request, and `broadcastSessionsList()` — mutation refreshes to every ready panel + the launcher): constructs one `GrokSessionStore` + one `ClaudeSessionStore` (cheap — just wraps `fs`/home dir/a log sink, no I/O at construction) and calls `buildMergedSessionsPage`; the merged index drives an **mtime-keyed read cache** (`sessionCache`, `readEntriesCached`) **shared across both backends** (ids from the two stores don't collide, and every cached entry carries its own `backend` field) so a re-open / load-more / search reads only entries whose underlying file actually changed — steady-state opens cost ~zero reads, for either backend. It posts `{type:"sessions", entries, activeId, dots, offset, total, totalAll, windowDays, nextOffset, hasMore, query}`, each entry carrying `backend` (`activeId` = the last-active tab's session, or null with no tab open). **Search** is server-side and complete: a non-empty `query` warms the whole catalog once (cache-backed, both backends) and filters by display name across **all** sessions, not just the loaded page. The cache is invalidated on `rename` (changes displayName without touching mtime), `delete`, `clearAll`, and the generated first-prompt title. **Live-session synthesis (open-too-early fix):** a brand-new session has *no* file on disk yet for either backend, so the merged index can't see it — opening history the instant a session goes live would drop the active row entirely (and the previous top session would masquerade as the whole list) until the file lands. So on the **first, unfiltered page** the builder injects a synthesized `liveSessionEntry` (pinned newest-first, tagged `backend: "grok"` — only grok sessions live in the in-memory `pool` today; a live `Session` has no `backend` field of its own yet, that's WP3) for any live `pool` member whose `activeSessionId` isn't in the merged index, naming it from the best in-memory source (generated/renamed `customName` → first user message → `"New session"`); the next refresh replaces it with the real entry once the file lands. `hasMore` is computed from the on-disk page *before* injection (load-more pages are disk-only), and these ids are never on disk so they can't duplicate onto a later page. Mirrors the existing dot-patch loop that already covered not-yet-persisted pool members. **Delete/clear-all are backend-aware:** `deleteSession(id, name, backend)` routes to the right store (the webview sends the row's own `backend`, defaulting to grok when absent); `clearAllSessions` sums each store's clearable count and calls `removeAll` on both, purging the shared cache/overrides for every removed id regardless of which store it came from.

**The load-more cursor is the host's authoritative `nextOffset`, not a client-side row count (WP3, docs/plans/capability-surfacing-and-history-ux.md § Thread 3).** `buildMergedSessionsPage` returns `diskCount` — the number of **index slots** (`offset..offset+limit` of the windowed list) THIS page consumed, before `buildSessionsMessage` prepends any synthesized live row; `nextOffset = offset + page.diskCount`. `diskCount` deliberately counts slots consumed, not rows `readEntries` managed to parse: `readSessionEntries` (`sessions.ts`) silently drops an id whose `summary.json` is unparseable/locked (plausible on Windows, where grok re-persists a live session's file) — counting only successfully-read rows would under-advance `nextOffset` and re-read already-consumed slots, or (if a whole page failed) get `nextOffset` stuck at `offset` forever while `hasMore` stays true. Both webviews (`media/chat.js`'s history popover and `media/launcher.js`) page off this field (`state.sessionNextOffset` / `state.nextOffset`), not `state.sessions.length`/rendered row count — the latter is the shared-pattern bug the review found: a client computing its own next offset over a list the host has since mutated (via injection) overshoots by the injected rows' count and permanently skips a real disk session at every page boundary.

**The activity-bar launcher is a windowed, paged, scrollable list with a render ceiling — not a 7-row cap.** `grok.launcherHistoryDays` (default 30, `0` = unlimited) filters the merged index to sessions active within that window (`sinceMs`, computed by the pure `daysToSinceMs` in `session-store.ts` — `0` days short-circuits to `sinceMs: undefined` *before* any `Date.now() - …` arithmetic, so "unlimited" can never collapse to "everything excluded"); `postLauncherSessions` threads `sinceMs` **and** `pinnedIds` (every live pool member's `activeSessionId`, from `livePinnedIds()`) through `buildSessionsMessage` — `replySessionsList` (the chat popover) passes neither, so it stays full and unwindowed. **`pinnedIds` exists because a live session isn't exempt from the window "by construction"** — that claim only holds for a session with no file on disk yet; a live session that IS on disk with a stale mtime (a resumed old session, or a narrow `launcherHistoryDays`) would otherwise drop out of the launcher along with its status dot, the only ambient signal a background tab needs the user. **Two totals, two jobs, never swapped:** `total` is the *windowed* count (drives paging, `hasMore`, and the ceiling notice); `totalAll` is the *unwindowed* count (drives ONLY the "Clear all" footer, since `clearAllSessions` deletes every session for the workspace, not just in-window ones) — a footer keyed off `total` would hide a still-working destructive action, a ceiling notice keyed off `totalAll` would name a count the windowed list can never reach. `buildMergedSessionsPage`'s returned `index` stays **unwindowed** regardless of `sinceMs`/`pinnedIds` — windowing it too would make an out-of-window live session look "absent from disk" to the live-synthesis check above and produce a duplicate row. The launcher pages `LAUNCHER_PAGE_SIZE = 50` rows at a time (a scroll-near-bottom listener, guarded by `hasMore`/`loading`) up to a hard `LAUNCHER_MAX_ROWS = 500` ceiling, past which it renders a muted `.launcher-list-notice` ("Showing the first 500 of `total` in the last `windowDays` days…") pointing at the chat popover (the surface with search + full pagination) instead of auto-loading further — deliberately not virtualization. **Sticky-window refresh:** `broadcastSessionsList()` pushes an unfiltered offset-0 page (at most `LAUNCHER_PAGE_SIZE` rows — `postLauncherSessions` with no explicit `limit`) on every send/rename/delete/tab-open-or-close; naively rendering it once more than one page is loaded would collapse the list back to 50 rows and jump to the top on every message. So the launcher detects that case — gated on the host's own disk cursor (`state.nextOffset`, from the *last* reply, exceeding `LAUNCHER_PAGE_SIZE`; a mirror of `LAUNCHER_PAGE_SIZE` lives in `launcher.js` purely for this comparison, with a source-text parity test against `sidebar.ts`'s copy), **not** on comparing the incoming page's size against what's rendered — that comparison fires on ANY shrink, including a plain delete while only one page is loaded (a needless round trip), and re-requesting `state.sessions.length` rows can include host-injected live/synthetic rows that aren't real disk pagination, letting the "loaded window" creep upward every refresh while one is present — and re-requests the WHOLE loaded window in one call, `{offset:0, limit: state.nextOffset}` (the disk cursor, not the rendered row count), instead of rendering the truncated page. This is *why* `postLauncherSessions` caps the client's requested `limit` at `LAUNCHER_MAX_ROWS`, not `LAUNCHER_PAGE_SIZE` (or that re-request would itself get truncated back to one page). A `pendingWindowRefresh` flag, set before the re-request and cleared on the next `sessions` message, is a **mandatory loop guard** — the re-request's own reply is *also* an offset-0 page whose `entries.length` equals the loaded count, which would otherwise re-satisfy the same trigger and recurse forever.

**Webview** (`media/chat.js` / `media/launcher.js`): `offset === 0` replaces the list, `offset > 0` appends (de-duped by id); a scroll-near-bottom listener requests the next page off the host's `nextOffset` (`hasMore`/loading guards keep it to one request per boundary); the search box posts a **debounced** (180ms) `listSessions` with the query; a host-driven refresh that arrives unfiltered while a search is active triggers a **sticky-search** re-request so the filtered view isn't clobbered (the launcher's analogous "sticky-window" refresh is described above). The "Clear all" footer shows when any non-active session exists (loaded *or* on a later page, via `total` for the popover / `totalAll` for the launcher). **Backend badges:** the pure `backendBadgeLabel` (`media/webview-helpers.js`, shared by both surfaces) renders a small `.history-row-backend` chip (VS Code `--vscode-badge-*` tokens, no hardcoded colors) — since docs/plans/capability-surfacing-and-history-ux.md § Thread 4 it labels **both** backends ("Grok" / "Claude"), a deliberate reversal of the original quiet-for-grok idiom **for this row only**: once rows from both backends are interleaved by recency in one scrollable list, every row needs per-row disambiguation, not just the secondary one. A missing/legacy `backend` field (a row that predates the field) also reads "Grok"; any other unrecognized value renders no badge at all. **The status-bar HUD does NOT follow this reversal — see § Status-bar HUD.** **Popover positioning:** `positionDropdownPopover` **right-aligns** the popover to the panel edge (`right: 6px`/`left: auto`) and grows it leftward, rather than left-anchoring with a one-shot width clamp. The clamp measured the popover width in a single `requestAnimationFrame` *before* the async session rows streamed in and widened it from `min-width` toward `max-width: 360px`, so the popover spilled off the right edge on the first open and only looked right on reopen (when `state.sessions` was already populated). Right-aligning is width-independent — no measurement, no reflow jump. It also **caps min/max width to the panel** (`maxWidth`/`minWidth` inline, overriding the CSS `min-width: 280px`/`max-width: 360px`) — `min(360|280, parentWidth − 2·EDGE)` — so in a narrow panel a long session name **ellipsizes** (the row already has `text-overflow: ellipsis` + `min-width: 0`) instead of the popover overflowing the *left* edge. Common-case sizing, not extreme (a panel narrower than the margins still clips). **Resize/hide:** a `window` `resize` listener re-runs `positionDropdownPopover` while the popover is open, so dragging the panel border re-fits it live (no close+reopen); and a `document` `visibilitychange` listener `closePopovers()` when the view is hidden (switching panel tab / extension), since a resize that happens while the webview is hidden fires no resize event — so the dropdown closes rather than reappearing stale on refocus (reopen re-measures).

**Perf simulation** (`npm run test:perf`, `test/sessions.perf.ts` via `vitest.perf.config.ts`) — opt-in, out of `npm test`/CI. Exercises the grok-only primitives directly (`indexSessions`/`readSessionEntries`/`listSessions`), unaffected by the merge layer above it. At N=5000 it asserts the op counts: first open drops file reads from **5000 → 100** (~98%), steady-state re-open is **0 reads** (mtime cache), search warms once then **0 reads**, with a modeled-latency projection (~3250ms → ~310ms) and a real in-memory parse-cost wall-clock (~2.7x, disk-latency-free lower bound).

**Resuming a Claude row is wired (WP5).** The webview sends the clicked row's own `backend` on `resumeSession` (`media/chat.js`/`media/launcher.js`, mirroring the `deleteSession` pattern — omitted for a legacy/grok row with no `backend` field), `openTabForId(id, backend)` sets `session.backend` before `startSession` runs, and `displayNameForId(id, backend)` reads the right store for the pre-spawn tab title. `session/load` needed no `acp.ts` change — it's a generic wire method the adapter already speaks identically to grok (verified by `research/claude-acp-resume-probe.cjs`: replay reconstructs user/assistant turns and every tool call with `kind` intact — see § ACP surfaces). Token usage on resume is wired for both backends: `ClaudeSessionStore.readTokenUsage` reads the **last** `type:"assistant"` record's `message.usage` from a bounded 256KB tail of the `.jsonl` and sums `input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens`. The cache fields are the bulk of the number — omitting them understates context usage by orders of magnitude (a real record: 2 + 696 + 474_901 + 291 ≈ 476K against Opus's 1M window). The tail bound was validated against the 12 largest real sessions on disk: all 12 hit, worst case 17KB from EOF. No usage record in the window ⇒ `undefined`, never a misleading 0.

## Status-bar HUD

Session state used to live only in webview-internal surfaces — model + effort two clicks deep in the gear popover, mode on the bottom-right button, context usage in the composer donut. None of it is visible while you're in a *code* editor. A native `StatusBarItem` (right-aligned, priority 100) now mirrors the **active** session: `$(sparkle) Grok Build · Medium · Agent · 41%`, with `$(loading~spin)` as the lead glyph while that session is mid-turn and a trailing `$(bell) N` badge (+ `statusBarItem.warningBackground`) when **any** session is waiting on the user. It hides entirely when no chat is open and nobody is waiting; clicking reveals the active chat (or opens the launcher).

The view is built by the **pure** `computeStatusBar` (`src/status-bar.ts`, no `vscode` import — importing `BackendId` from the equally framework-free `backends.ts` doesn't compromise that) so it's unit-tested like every other policy module; the impure `GrokSidebar.updateStatusBar()` gathers the live state and copies `text`/`tooltip`/visibility over. State sources: `backend` = **`Session.backend`** (grok stays the quiet default — undefined behaves exactly like `"grok"`; only Claude gets an explicit `Claude ·` segment + a `Backend: Claude Code` tooltip line); model = `client.currentModelId` resolved through `resolveModelId` → `availableModels[].name` (the **versioned-id gotcha** applies here too — `grok-build-0.1` isn't in the list); effort = **`Session.effort`** (`src/session.ts`) — per-session state, not the shared config (see the next paragraph); Claude has no effort axis at all, so the whole `Effort: …` tooltip line (not just the text segment) is omitted for it rather than showing a meaningless "Effort: CLI default"; mode = the derived `displayMode(session)`; context % = `client.lastMeta.totalTokens` over the active model's `_meta.totalContextTokens`; working = `session.status`; needs-you = a count of pool members at `status === "needs-you"`. Refresh hooks mirror the ones that already drive the webview toolbar: `setActive`, `setStatus`, `postMode`, the `modelChanged`/`promptComplete` client handlers, `disposeSession`, `onPanelClosed`'s re-home, and `logout`. The item is registered on `context.subscriptions` (VS Code disposes it); its click command `grok.revealActiveSession` is registered but deliberately **not** declared in `contributes.commands`, so it never clutters the palette.

**The HUD deliberately stays quiet for grok even though the history row now labels both backends (docs/plans/capability-surfacing-and-history-ux.md § Thread 4, Resolved decision 2).** `backendBadgeLabel` used to be the one place this idiom lived; since WP3 it labels both backends on every history row (see § History pagination), but `computeStatusBar` was **not** changed to match, and `test/status-bar.test.ts`'s existing quiet-for-grok assertions are the guard against a future "harmonize the two" cleanup. The two surfaces have genuinely different jobs, not a leftover inconsistency: a history list interleaves rows from both backends by recency, so every row needs per-row disambiguation; the status bar is one always-visible, width-constrained item describing a single open session whose model is already named — an explicit "Grok ·" segment there would just be noise in the common case.

**Reasoning effort is per-session, not global (`Session.effort` in `src/session.ts`).** `grok.defaultEffort` used to be read live at spawn AND written by the effort picker (`ConfigurationTarget.Global`), so changing effort in one tab silently changed it for every other tab, present or future — a real bug once every session is its own editor tab. Now `grok.defaultEffort` is only **the default for a brand-new tab**: `startSession` seeds `session.effort` from it the first time a session spawns (`undefined` marks "not yet chosen for this session," so a same-tab restart triggered by an effort change keeps its own value instead of reverting to the config default), `buildGrokAgentArgs` is called with `session.effort`, and `setEffort` in `sidebar.ts` sets `session.effort` and restarts *that* session only — it no longer writes the global config. Two tabs can run different efforts simultaneously; each tab's own title shows it via `composeTabTitle` (see the `sessions.ts` row in § Module map).

**`grok.notifyWhenWaiting`** (default **false** — opt-in) pairs with it: when a session in a **background** tab raises a permission request, a question, or a plan to review, a passive `showInformationMessage` offers *Go to session*. It never calls `reveal()` on its own — auto-focusing on a permission request is the exact focus-stealing failure the auto-opened diff-editor tab caused (see § ACP surfaces → `request_permission`), and it would also churn the `retainContextWhenHidden:false` teardown/replay cycle. Nothing fires for a tab the user is already looking at (`session.panel?.visible`).

## Token surfaces — three numbers, three jobs, never conflate them

| Surface | Quantity | Source | Moves when? |
|---|---|---|---|
| Launcher header `N tokens` (above **New session**) | **Grokbit's own development cost** — every token every maintainer has spent, in any agent session, changing this repo | `DEV_TOKENS_TOTAL` in the generated `src/token-metrics.ts`, posted once by `postLauncherMeta` on launcher `ready` | only when a maintainer regenerates the ledger and ships a new build |
| Composer context donut | the **active session's** current context | live `_meta.totalTokens` (`tokenUsage` message) | every completed turn |
| Status-bar `%` | the active session's context over its model's window | live `_meta.totalTokens` / `availableModels[].totalContextTokens` | every completed turn |

**The shipped extension performs no token computation at all for the first row, and that is the whole design** — the user's contract is *"This is a grokbit development number. User activity will never effect this number."* Any runtime meter fed by the viewer's own sessions violates it by definition, so `computeLifetimeTokens`/`lifetimeTokensCache` and the two `sessions.ts` exports that fed them (`readWorkspaceTokenUsage`/`mergeWorkspaceTokenUsage`) are **deleted, not refactored**. There is nothing here to refresh, cache or invalidate; `postLauncherMeta` takes no options and has exactly one call site. What it replaced was non-monotonic by construction (a sum over a *mutable* directory listing — six delete paths, four of which never refreshed the badge), measured *current context* rather than tokens spent, and cost a full `readdirSync` + parse of every `signals.json` on **every completed turn**. Read `docs/adr/0003-development-token-ledger.md` before "fixing" this back into a live per-user meter — that instinct is the standing risk, and `test/token-metrics.test.ts`'s *data module — no imports, no logic* assertion is the executable guard.

**The pipeline** (dev-time only, none of it ships): `scripts/aggregate_token_usage.py` scans `~/.claude/projects/<slug>/**.jsonl` and `~/.grok/sessions/<encodeURIComponent(cwd)>/*/signals.json` for this repo (and its subdirectories), and writes `docs/metrics/token-usage.json` + `src/token-metrics.ts`. Run it with `npm run metrics:tokens`; the install scripts also run it **non-fatally** between the version bump and `npm run package`, so a missing Python or an aggregator error can never block a rebuild or release. Two buckets with **honestly different accountings**, each tagged in the JSON: `claude_sessions` is exact billed tokens (`input + output + cache_read + cache_creation` per assistant record — omitting the two cache fields understates by orders of magnitude), `grok_sessions` is a **lower bound** (`contextTokensUsed + totalTokensBeforeCompaction`; grok persists no per-turn record on disk). `grok_session_estimate` there is a deliberate mirror of `sessionTokenEstimate` (`src/sessions.ts`) — change one, change both. **Records are bucketed by their own `sessionId`, never by file path** (a workflow subagent transcript is written under *every* parent session that ran it — same filename, three parent dirs observed, each copy carrying its own parent's `sessionId` and its own `message.id`s), and each write is a **union of ids with a per-session `max`** with the headline total recomputed from the map: a blind full recompute would reproduce the original non-monotonicity one layer up, since transcripts get pruned and a second maintainer holds a different subset. A scan that finds nothing writes nothing. **Privacy is load-bearing** — transcripts are never committed, and the aggregate carries session ids, integers and two fixed accounting tags, no free text. `scripts/verify_token_aggregator.py` (fixture-driven, `fixtures/token-usage/`, manual — `npm test` and CI stay Python-free) asserts all of the above; see § Build + test and `docs/metrics/README.md`.

## Grokbit Actions + the bundled skill suite

The capability browser's menu is **Grokbit Workflows** (top-bar label), and by default it renders (1) the **bundled Grokbit suite** — `grokbit-explore` → `grokbit-plan` → `grokbit-implement` → `grokbit-test` → `grokbit-document` → `grokbit-ship` (the one-shot orchestrator: the whole pipeline with a mandatory human checkpoint after plan, Ultimate `/ship` lineage; it **coexists** with the phase tiles rather than replacing them), present and identical on both backends — as bordered tiles (display labels **Explore**… in cyber green), plus (2) **User Workflows** — backend-native saved multi-agent scripts (`kind: "workflow"`): Grok `.grok/workflows/*.rhai`, Claude Code `.claude/workflows/*.js`, discovered by `scanCapabilityRoots` with pure meta parsers (never executed in the extension). Workflow tile **labels** are Title Case (e.g. **Create Workflow**); `name`/invoke stay kebab. On Grok, the synthetic Create tile opens the **Workflow Builder** overlay (required name + scope toggle, goal, phase/agent canvas per ADR 0004); **Craft with AI** auto-sends `/create-workflow` with a structured brief, shows a working status on the builder, then loads the proposed workflow back for editing. Skills / Agents / Commands still ship in the host payload but are filtered out of both UI mounts by the pure `visibleCapabilityGroups` allowlist (`CAPABILITY_VISIBLE_KINDS = ["grokbit", "workflow"]` in `media/webview-helpers.js`) unless `grok.actionsScope` is `all`. Formats are **not** interchangeable across backends. SoT: [docs/plans/grokbit-actions-and-bundled-skill-suite.md](docs/plans/grokbit-actions-and-bundled-skill-suite.md); filter + tiles: `.grokbit/plans/actions-workflow-tiles/`; User Workflows: `.grokbit/plans/user-workflows-tile/`.

**Each suite tile states its agents and its review count on its face** (`Agents  Business Analyst · Systems Analyst · Solutions Architect · Plan Reviewer` / `Reviews  3 adversarial rounds + 1–2 plan passes`), so the six phases are distinguishable without opening **Details**. Source is the committed `SUITE_TILE_META` (`src/skill-suite.ts`) → `CapabilityItem.meta` → `capabilityGroupsView` → a `.capability-row-meta` block in `buildCapabilityRow`. Three things about it are load-bearing. **`reviews` is a phrase, not an integer** — the caps genuinely differ in kind (Plan runs 3 adversarial rounds *plus* 1–2 plan-level passes; Test runs 7 bounded loops one of which has no escape), so one number would be an invented comparison; the parity test only requires every numeral in the phrase to appear in that skill's `## Loops and caps`. **Ship carries `agents: []` + `agentsNote`** — it has no roster of its own and its guide says so verbatim; the note lives in the manifest rather than as a renderer fallback so the copy stays testable. **The renderer guards on `Array.isArray(item.meta) && item.meta.length`, never on `kind === "grokbit"`**, and `capabilityGroupsView` is an explicit whitelist — a host field not added there is silently dropped before it reaches the DOM, which is the one way this feature fails with no error anywhere.

**The suite ships in the vsix and is provisioned to the home tier.** `resources/skills/` is not excluded by `.vscodeignore` (an exclude list — `resources/` already carried the extension icons), so it ships automatically; verify with `npx @vscode/vsce ls | grep resources/skills`. On activation `provisionSkillSuite` (`extension.ts`) copies it into **`~/.grok/skills/`** and **`~/.claude/skills/`** — *both*, regardless of which CLI is installed, since a directory for an absent CLI is inert and the suite is then already in place if the user installs it later. **Shipping the files makes them available; copying them out is what makes them runnable** — a skill only exists to a CLI if it sits on that CLI's own search path (`CAPABILITY_ROOTS`). Home tier rather than workspace tier so one run covers every project and nothing is written into the user's repo; the disclosed cost, stated in the `grok.skills.provision` setting description and the suite README, is that these skills also appear in CLI sessions started outside the extension. `grok.skills.provision: "off"` disables it end to end.

**Copy, not symlink,** and the deleted `install.sh` is why: on native Windows its symlink silently failed, its copy fallback ran, and later edits to the canonical copy stopped propagating with no signal. The extension owns both destination copies and rewrites them wholesale on version change, so a link buys nothing. `shouldProvision` is an **inequality, not "bundled is newer"** — a downgrade must re-copy too, because the correct suite for an installed extension is the one that shipped with it. Provisioning is fully async, never awaited by `activate`, and never throws into it: every failure mode (no home dir, read-only `~/.claude`, partial previous run) degrades to the same correct outcome — the group is simply absent, exactly as if the setting were off.

**Suite membership is a post-scan reclassification, not a new root — and the ordering is load-bearing.** Provisioning writes into the same home-tier skills directory the ordinary `skill` roots already scan, so suite items arrive as `kind: "skill"` and cannot be told apart by root. `applySuiteKind` re-keys them to the new `"grokbit"` `CapabilityKind` (`CAPABILITY_KIND_ORDER` leads with it), and it runs **after `scanCapabilityRoots` and before `buildCapabilityGroups`**: `dedupeByPriority` keys on `` `${kind}|${name}` ``, so a workspace-tier and a home-tier `grokbit-plan` collapse to one item only while both are still `skill`. Re-key first and they carry different keys, both survive, and the same skill renders twice — once per group. `test/skill-suite.test.ts` asserts both orderings explicitly. **Re-keying requires two conditions, name membership AND path containment in a directory this extension actually wrote** — name alone would let any repo ship `.grok/skills/grokbit-plan/SKILL.md` and have it promoted into the group the UI presents as Grokbit's own, and since workspace items win `dedupeByPriority`, that impostor would be the *only* row rendered. A deliberate workspace fork stays `kind: "skill"` (discovered by the host, not badged as ours) — and because Actions only renders `grokbit`, that fork is invisible in the menu (known limit; still reachable via `/` if the CLI registers it).

`CAPABILITY_FEATURED.grokbit` (`media/webview-helpers.js`) lists **every** member, in the same pipeline order as `SUITE_SKILL_NAMES` — `partitionFeatured` reorders matched items into that array's order, and it is the only thing that sorts the group, so the two arrays must stay in step. Listing all of them means `featuredCount === items.length` and the group renders no "Show all" expander: a five-step pipeline that hides its last steps behind a link would teach the workflow wrong. The old agentic-team `plan`/`implement` names were **removed** from the `skill` featured list in the same change — they were this repo's own `.grok/skills` suite, which the bundled one replaces, and `.grok/`/`.claude/` are now gitignored (untracked, files kept on disk) so the extension ships exactly one skill set.

## Workspace harness hooks

Optional Python hooks (GrokForge template lineage, ADR 0001) vendored into `resources/hooks/grok/` and installable into the **open workspace's** `.grok/hooks/`: a `Stop` gate that runs the `AGENTS.md` Project Test Commands Lint + Unit rows when the session changed a file, `protect_paths` (PreToolUse deny for secrets / `.git` / the hook layer / `AGENTS.md` itself), a `mark_changed` PostToolUse marker, a `session_start` reset, and a `record_session_tokens` SessionEnd capture. They are a **backstop, not a protocol** — nothing here replaces plan → implement accuracy, and the extension says so in the setting description, the install notice and the bundle README.

**Workspace-first, opt-in, and reversible.** Unlike the skill suite (home tier, every project, `auto` by default), hooks land per-repo and `grok.hooks.provision` defaults to `off`: a gate that runs a repo's test suite on every turn is that repo's decision. Uninstall is `rm -rf .grok/hooks/`; nothing is written anywhere else in the user's tree.

**Three preconditions, each surfaced rather than assumed.** (1) `/hooks-trust` — untrusted project hooks never fire. (2) **A Python interpreter** — every wired command is `python "<script>.py"`, and most macOS/Linux boxes have only `python3`, so `installHooks` probes `python` then `python3` (`pickHookInterpreter`) and rewrites the copied `settings.json` accordingly (`retargetHookSettings`); finding neither still installs but reports a *warning*, never the success notice, because a gate that can't start is worse than no gate. (3) **A ledger consumer** for `record_session_tokens.py` — it writes `docs/metrics/pending-commit.env`, which only a repo running `scripts/prepare_commit_metrics.py` consumes, so `has_ledger_consumer` makes it a no-op everywhere else. Installing hooks must never conjure a `docs/metrics/` directory in a project that has no use for one; `test/hook-parity.test.ts` asserts that guard precedes the first directory-creating write.

**`installHooks` ordering is the whole design** (`src/hook-suite.ts`). The bundle manifest is validated **before** the backup-and-remove step, so a damaged vsix can never delete a user's hooks and leave nothing in their place; and the version marker is written **last, only on a provably complete copy**, so a partial or empty install is never recorded as "version current" and skipped forever after — a dead gate reporting itself installed is the exact failure this ordering exists to make impossible. Overwrite safety keys off `hasNonMarkerContent` (**any** entry that isn't our marker), not `dirLooksLikeHooks` (`.py`/`settings.json` only): Grok discovers wiring from `*.json` and a repo may keep `.sh`/`.ps1` hook scripts, so the narrower test would let the auto path write over a curated directory it simply didn't recognise. `dirLooksLikeHooks` survives for the *other* question — dual-stack detection.

**Dual-stack is warned, never resolved.** `detectDualHookStacks` logs once per activation when both `.grok/hooks/` and Claude hooks are present (see § Known limits); the extension never renames a user's Claude agents.

- **Full-canvas layout (docs/plans/session-tab-ux-overhaul.md § WP1).** A session tab uses the **whole editor width by default — no width setting, no centred column.** `.messages`/`.composer` were already full-bleed; the actual "narrow ribbon" complaint came from a handful of `max-width: 360px` leftovers from when chat lived in the activity bar (`.session-setup-card`, `.capabilities-panel`) plus the welcome tagline and onboarding card, all now removed or raised (`.welcome-tagline` → `min(100%, 60ch)`, `.onb` → `min(100%, 560px)`). Filling a wide canvas means **more columns of real content, not wider cards**: `.capability-group-items` is an intrinsic grid (`repeat(auto-fit, minmax(min(100%, …), 1fr))`) that collapses to one column below its min track — byte-for-byte the old stacked rendering — and flows into more columns as the tab widens. **The `min(100%, …)` clamp is mandatory wherever a track/basis has a pixel floor**: a bare `minmax(300px, 1fr)` (or a bare `300px` flex-basis) overflows a ~250px split-editor tab, turning a full-canvas fix into a horizontal-scroll regression at the narrow end. **`#welcome-grid` (wrapping `#capabilities-panel` in `getHtml`; Session setup lives on the top-bar chip, not a welcome tile) is a wrapping flex row**, not equal `1fr` auto-fit tracks (docs/plans/actions-panel-layout-and-dynamic-capabilities.md; ADR 0002 § Amendment 2026-07-30). Its mode line is the one that must never be wrong: Plan states a plan is drafted before anything changes, Agent states Grok may still ask before editing files or running commands, and **Auto-accept states edits apply without asking and deliberately never claims files are protected** — a false safety statement would be worse for the non-technical user this strip targets than the blank canvas it replaces. Unlike the capability panel it has no async data dependency (`state.backend`/`state.currentModeId` always have sane defaults), so it needs no "payload not arrived yet" branch, and it must not resurrect the `74e923a`-removed `#welcome-starters`/`.welcome-starter`/`.welcome-task-chip` chrome (`test/friendly-ui.dom.test.ts`) — it is prose describing shipped behaviour, not an invented prompt catalogue. See `docs/adr/0002-session-tab-layout-and-empty-canvas-policy.md` for why the whole welcome canvas renders locked instead of hidden during priming. The webview requests `listCapabilities` from the **`initialState` handler**, not `ready` — `grok.showCapabilities` only arrives inside `initialState`, which `postPanelConfig` sends *in response to* `ready`, so a gate evaluated at `ready` time would read a value that doesn't exist yet; since `initialState` is re-posted on every reveal of a torn-down hidden panel, this doubles as a refresh-on-reveal. The popover carries the same two `stopPropagation` guards every sibling popover has (`#capabilities-btn`'s `onclick` + a `click` listener on `#capabilities-popover` itself) — miss either and the opening click bubbles to the document-level `closePopovers()` and immediately re-hides it. **A second, plainly-labelled door lives beside the composer** — `#add-btn`'s popover (`openAddPopover`) gains a *"Browse Grokbit Actions…"* item wired straight to `openCapabilitiesPopover()` (which does its own `closePopovers()`, so the item's own handler must not call it again or it would immediately hide the popover it just opened), gated on `state.showCapabilities` so it's never a dead-end click after the welcome canvas — and its own door — is gone (`clearWelcome`). Same two `stopPropagation` guards as every sibling popover. The composer placeholder (`updateComposerPlaceholder`) is backend-aware (`"Ask Grok…"` / `"Ask Claude…"`) — it used to hardcode "Grok" even on a Claude tab. **A `Refresh` affordance sits in both mounts' heads** (`.capabilities-head` on the panel, `.studio-popover-head.with-action` in the popover; `buildCapabilitiesRefreshButton`): discovery already re-scans the user's own disk on every request, but the canvas renders from the payload that arrived at `initialState`/reveal time, so a skill written mid-session — by the user, or by the *agent* via `fs/write_text_file`, which fires no editor save event — was invisible until a tab switch. It re-posts the **existing** `{type:"listCapabilities"}` (no new message, no new host method, already covered by the `showCapabilities` host gate) and is suppressed while `locked`, for the same reason the rows are. `CAPABILITY_GROUP_CAP` is **100**, not 40 — `CAPABILITY_SCAN_FILE_CAP = 300` is the real bound on the work, both mounts scroll, and `+N more` is a dead end with no "show the rest", so a low cap just hid the user's own skills.

The Actions **popover** leads with a *Session controls* group holding an **Auto-accept** switch, built by the pure `sessionToggleGroup({modeId, locked})` (`webview-helpers.js`) in the same group shape `capabilityGroupsView` emits. **The host never produces this group** — it's appended at render time from the webview's own `state.currentModeId` and posts the existing `{type:"setMode", modeId}`, so it holds no state of its own, `src/capabilities.ts`/`listCapabilities`/`CapabilityKind` are untouched, and it cannot drift from the mode button or the Session setup popover (the `modeChanged`/`setBusy`/`backendChanged` handlers re-render the open popover body). `buildCapabilityRow` branches on **`item.control === "switch"`** — deliberately *not* on `item.kind`, preserving the standing rule that the renderer never branches on kind strings — delegating to `buildCapabilityToggleRow`, which reuses the gear popover's `.popover-switch`/`.popover-switch-knob` markup verbatim (`role="switch"`, `aria-checked`); no new switch visuals, and no click handler at all when locked. **Auto-accept is one value of a TRI-state mode** (`agent`/`plan`/`yolo`), so a two-state switch has to name its OFF target explicitly: the item carries `onModeId: "yolo"` / `offModeId: "agent"`, and from Plan mode it renders off with a description saying that turning it on *leaves* Plan mode — allowed, since the host's `setMode("yolo")` already drops `planActive` and the Mode segmented control permits the same transition; a disabled switch there would behave differently from the control it mirrors. **Mount policy: popover only, never the welcome canvas** — mode is already on the top-bar Session setup chip and the mode button, so a switch on the Actions panel would be two controls for one piece of state on one screen; `test/capabilities.dom.test.ts`'s "the welcome-canvas panel renders no switch" case is the executable guard for that decision.

On a real skill/command install every group rendering in full was a wall of rows, so each group now shows a small **featured** set by default with the rest behind an expand link. Data, not logic: `CAPABILITY_FEATURED` (`webview-helpers.js`) maps `CapabilityKind` → lower-cased featured names, matched case-insensitively on `item.name` by the pure `partitionFeatured(items, kind)`; `capabilityGroupsView` calls it per group and stamps the result's `items` (featured items moved to the front **in the configured order**, everything else keeping the host's own order behind them) and `featuredCount` onto the returned group. **Every configured name is listed under every kind it could plausibly discover as, not just the one the operator had in mind** — `mergeAcpCommands` keeps the DISK kind on a name collision, and every disk root (`src/capabilities.ts`) yields `skill`/`agent`, never `command`, so an install where `docx`/`pptx`/`cold-review`/etc. ship as real skill directories would otherwise land in Skills (matching neither `plan` nor `implement`) while Commands matches nothing and silently degrades to plain first-N truncation — the exact failure mode the feature exists to prevent, with no warning it happened. So the Skills list is every configured **command** name, dual-listed (the old agentic-team `plan`/`implement` entries were removed when the bundled suite replaced that repo-local suite — see § Grokbit Actions), the Commands list is `cold-review`/`init-repo`/`docx`/`pptx`/`pdf`/`create-workflow`/`workflow`/`deep-research`/`always-approve` — **and `alawys-approve`**, kept as a second entry because the operator's own request had that typo — and the Agents list is `explore` (grok's built-in agent type) **and `explorer`** (`.claude/agents/explorer.md` in this repo) — one intent, two spellings, same "costs one array entry and cannot be wrong" reasoning throughout. No configured list for a kind, or none of it installed on this machine, falls back to the first `CAPABILITY_FEATURED_FALLBACK` (**5**) items — never collapses to zero rows, so the panel stays compact for everyone, not only on the operator's own machine; that fallback path returns a fresh array (`list.slice()`), matching the matched path, per `partitionFeatured`'s documented-pure contract. `sessionToggleGroup`'s group never passes through `capabilityGroupsView`, so it carries no `featuredCount`; `appendCapabilityGroups` falls back to "show everything" for that case (`typeof group.featuredCount === "number" ? … : group.items.length`) — a structural consequence of the data shape, not a branch on `group.kind`, so it gets no expand link, same as any group no bigger than its own featured/fallback count. The renderer slices, it never re-sorts: `appendCapabilityGroups` renders `expanded ? group.items : group.items.slice(0, featuredCount)` and appends a centred `.capability-expand` button (`Show all N` / `Show less`, `aria-expanded` tracking state, focus-visible outline matching `.capabilities-refresh`) **after** `itemsEl`, never inside it — `.capability-group-items` is an `auto-fit` grid, so an in-grid link would render as a stray cell. **Its click updates BOTH mounts, not just the one clicked** — the welcome canvas and the Actions popover can be on screen at once (the popover overlays the canvas), so the handler captures `!expanded` at render time (never toggles the live state value — both mounts re-render off the same state right after, so a stale flip in one after the other already flipped it would undo the click), writes `state.capabilitiesExpanded[group.kind]`, then calls `renderCapabilitiesPanel()` unconditionally and `renderCapabilitiesPopoverBody()` only `if (capabilitiesPopover && !capabilitiesPopover.hidden)` — the same pairing idiom every other capability-state handler in the file already uses (`setBusy`, `modeChanged`, `backendChanged`). `state.capabilitiesExpanded` (`{[kind]: true}`) is shared by both mounts by design — they're two views of one list — so a re-render from any other trigger (`setBusy` lock/unlock, `modeChanged`, `Refresh`) reads the same state and never silently re-collapses a group the user opened; cleared only in `resetForNewSession` (a fresh session doesn't inherit the old one's expansion choice). `renderCapabilitiesPopoverBody` additionally captures `body.scrollTop` before clearing `innerHTML` and restores it in a `finally` (covering its several early returns) — the popover body is a bounded, scrolling `.studio-popover-body`/`.history-list`, and a lower group's expand link is below the fold by construction, so a naive rebuild would snap back to the top and strand the just-revealed rows off-screen. **Expand works while `locked`** — pure local display, unlike `Refresh` (a host round-trip) and row clicks (a composer seed), so nothing about the priming window makes it a lie; expanded rows stay `.locked` and unclickable, only their visibility changed. `+N more` (the host-cap `CAPABILITY_GROUP_CAP` overflow label) moved to render **only while expanded** — collapsed, it would read as a second, competing "there's more" signal alongside the expand link itself.

## Build + test

```bash
npm install
npm test         # 1336+ tests, ~3s, vitest — all grok-free (incl. happy-dom DOM tests + fake-CLI ACP integration tests)
npm run test:perf # opt-in session-history perf simulation (NOT in npm test/CI; see § History pagination)
npm run package  # → grokbit-<version>.vsix (clears older *.vsix first)
```

### Test taxonomy — three layers

There are **three** kinds of tests, and it matters which is which:

1. **`npm test` — grok-free unit/DOM/integration suite (1336+ tests).** Pure logic, happy-dom tests that drive the real `media/chat.js`, a real-`/bin/sh` TerminalManager smoke, and a fake-CLI ACP integration suite (`test/fixtures/fake-grok-acp.cjs`). **Never spawns the real `grok` binary.** Runs in ~3s with no network, no login, no subscription. This is the floor — every change keeps it green. (A separate opt-in `npm run test:perf` runs the session-history perf simulation — `test/*.perf.ts` via `vitest.perf.config.ts`, matched only by that config so it stays out of `npm test`/CI; see § History pagination.)
2. **CI — the *same* suite.** `.github/workflows/ci.yml` runs `npm ci && npm test && npm run package` on a clean Ubuntu box. **CI ≡ layer 1, verbatim** — there is no separate CI-only set. CI has no `grok` binary, no auth, no SuperGrok subscription, so it *cannot* run anything that touches the real CLI. That's the whole reason layer 1 is grok-free.
3. **`npm run test:live` — on-demand pre-release suite against REAL grok (`scripts/live-tests.cjs`).** Spawns the actual `grok agent stdio` and exercises the surfaces layers 1–2 can't: the real ACP handshake, a prompt round-trip, session restore, plan-mode enforcement, and the v1.4.x generative features (image gen, video gen; the subagent path is exercised opportunistically and SKIPs when grok doesn't delegate — it's deferred/research-only). It **reuses the real compiled modules** (`out/acp-dispatch.js`, `out/plan-gate.js`, `media/webview-helpers.js`) — it feeds genuine wire output through the same `isMediaGenToolCall`/`extractGeneratedMediaPaths`/`isSubagentToolCall`/`shouldBlockWrite` the extension uses, not a re-implementation. **Always run it before every release-to-`main` — it's a non-negotiable, standing part of the release gate; run it without asking** (it needs a logged-in grok + subscription and burns credits, so it must never be in `npm test` or CI, but it is mandatory before any tag/release). Flags: `--quick` (skip the slow generative tests), `--only=`, `--skip=`, `GROK_BIN=…`. A SKIP (no subscription, grok chose not to delegate, etc.) does not fail the gate — only a FAIL does. Real-grok **diagnostic probes** (`research/*.cjs`) remain manual one-offs for capturing wire shapes; the live suite is the repeatable gate.

**So:** local == CI (both grok-free). The real-grok tests are a separate, mandatory pre-release gate — always run before a tag/release (no need to ask), never on every commit.

### grok CLI version + updating

The native-Windows build (`irm https://x.ai/cli/install.ps1 | iex`) installs from the **stable** channel. The extension pins Windows to the supported build (`GROK_STDIO_DOWNGRADE_TARGET` in [src/cli-locator.ts](src/cli-locator.ts); see § Status → Grok CLI compatibility and `research/stdio-eof-regression.md` for the #22 pin and the exact versions). **grok does not auto-update.** Updating is the explicit `grok update` command: `grok update --check [--json]` checks without installing, `grok update` installs the latest on the current channel, `--stable` (default, weekly) / `--alpha` switch channels, `--version <X.Y.Z>` pins a specific build. Note: `grok update` can only rename the binary when no grok process holds it open, or it fails with *"cannot rename locked executable"* (`Access is denied. (os error 5)`). The extension's update path tears the whole pool down **and awaits each process's actual exit** before running the update — `kill()` only *signals*, and on Windows the OS releases the `grok.exe` lock a beat after the process finishes, so a too-eager update loses the rename. On Windows it `taskkill /PID … /T /F`-kills the process **tree** (grok backgrounds subagent/command children a parent-only kill would orphan, and those keep the binary locked), then retries the update once if a lingering lock still slips through (`isLockedBinaryError` in [src/cli-locator.ts](src/cli-locator.ts); see CHANGELOG 1.4.26). Re-run `npm run test:live` after any CLI update — the wire format is the thing that drifts.

## ACP surfaces implemented

- `initialize` → `session/new` / `session/load` → `session/set_model` → `session/prompt` lifecycle
- **Model switching is agent-aware.** Models belong to *agent types* — `grok-build`/`grok-build-plan` vs the `cursor` agent that owns the Composer models. The CLI binds the agent at spawn and locks it after the first turn (incl. our primer), so a live `session/set_model` only works within the same agent; a cross-agent switch errors `MODEL_SWITCH_INCOMPATIBLE_AGENT` ("Start a new session"). `switchModel` in `sidebar.ts` tries the live switch, and on that error (detected by the pure `isIncompatibleAgentError` in `acp-dispatch.ts`) persists the pick to `grok.defaultModel` and restarts — `newSession` re-applies the model *before* the primer runs, while the agent is still rebindable. No history → transparent restart; with history → the same Summarize/Just-Restart prompt as an effort change (shared `pickRestartMode`/`restartSession` helpers). **Empty-session cleanup:** a restart on a *primer-only* session (no real conversation — the common case when you flip models/effort a few times right after opening) gets the no-prompt transparent path *and* `discardRestartedEmptySession` deletes the abandoned grok session dir afterward, so repeated switches don't pile up identical primer-only sessions in history; the pure `carrySessionName` (in `sessions.ts`) moves any user rename (`customName`) from the discarded id onto the fresh one so the chosen name survives. The same cleanup runs on the effort-change empty-session branch (guarded so a dead client on a session *with* history keeps its history). The toolbar model label resolves IDs to user-facing names via the pure `modelDisplayName` helper. **Versioned-id gotcha:** grok's `set_model` (and session load on some builds) echoes a *versioned* id — a request for `grok-build` resolves to `grok-build-0.1`, which is **not** in `availableModels` (`grok-build`). Left as-is that breaks both the name lookup (shows the raw id) and the context-window lookup (falls back to the 200K default instead of grok-build's 512K); worse, that echo carries **no name/context of its own** — those live only in the model list. So `setModel` anchors to the *requested* id (the picker only ever offers list ids), which always resolves to a name + window; the pure `resolveModelId` in `acp-dispatch.ts` (exact → longest base-id prefix → input) is the fallback for grok-provided ids on `newSession`/`loadSession` (and a stale `defaultModel`). The context window is per-model (`_meta.totalContextTokens`: grok-build 512K, Composer 200K) and is recomputed in `chat.js` on every `modelChanged`, not just the initial session event.
- Streaming `agent_message_chunk` + `agent_thought_chunk`
- Sessions: list/resume via `session/load` (grok stores them at `~/.grok/sessions/<urlencoded-cwd>/<id>/`); rename/delete metadata in `context.globalState["grok.sessionMeta"]`. We never edit grok's own session files. **Per-session delete** is the trash button on each non-active row (launcher + dropdown; `deleteSession` → `deleteSessionDir`) — deleting a session with an open tab also closes that tab; the active session has no delete (the live CLI re-persists it, so it wouldn't stick). **Clear all** (#19) is a footer button (launcher + history popover, shown only when ≥1 non-active session exists) → `clearAllSessions` in `sidebar.ts`: a modal-confirmed sweep of every session dir for the current workspace *except every open panel's session* (each live CLI re-persists its own; the tab would also be orphaned), via the pure `clearSessions({fs, grokHome, cwd, exceptIds})` in `sessions.ts` (best-effort — a locked dir is skipped, not thrown), then purges the removed ids' `grok.sessionMeta` overrides and tears down any panel-less live pool members it deleted. **Scale (history pagination):** the list loads **one page at a time** (newest-first by last activity) so it stays fast with thousands of sessions — see § History pagination. Clear-all is the relief valve for an overgrown store; the pagination is the steady-state fix.
- Handlers (mandatory or the agent crashes): `fs/read_text_file`, `fs/write_text_file`, `terminal/{create,output,wait_for_exit,kill,release}`
- `session/request_permission` → chat card with `allow-always` / `allow-once` / `reject-once`; a `kind:"edit"`'s diff renders **inline in the card** (pure `computeLineDiff` in `webview-helpers.js` → `renderInlineDiff` in chat.js: VS Code diff-theme colors, 3 context lines, long unchanged runs collapse behind a clickable gap, 800-row render cap), and the same block is toggleable from an edit tool row ("view diff"). **Never a separate diff-editor tab** — the old auto-opened tab covered the chat webview in the same editor group, and because a hidden webview is torn down + replayed on reveal (`retainContextWhenHidden:false`), the replayed pending card re-opened the tab in a focus-stealing loop (closing the diff revealed the chat → replay → diff back). The catch-all ACK'd unknown server requests with `{}`, which grok's deserializer rejects with "missing field `outcome`". Now handled: the card renders each question's options (single question + single-select resolves on one click; otherwise pick-then-Submit; Skip → cancel) and replies `{ outcome: "accepted", answers, annotations }` (or `cancelled`). `answers` is keyed by question text → chosen label. On answer the card collapses to the question + a green `✓ <choice>` (so it's clear grok received it). - **Plan mode is enforced client-side** (mirror of YOLO). The CLI's `x.ai/exit_plan_mode` still treats any client response — result *or* error — as approval (re-verified broken in 0.2.3), so we don't rely on it. Instead `src/plan-gate.ts` gates the two *mandatory* server→client choke points: `fs/write_text_file` (block writes resolving inside the workspace cwd) and `terminal/create` (block anything not on the read-only allowlist). grok's own `~/.grok/sessions/<…>/plan.md` write lands *outside* the workspace and is allowed (and snooped to recover the plan text — `exit_plan_mode` arrives with `planContent: null`). Approve → drop the gate + send an "implement it now" follow-up prompt; Keep planning → gate stays up. Entering plan mode *any* way (incl. agent-initiated `current_mode_update: plan`) raises the gate; it's lowered only by explicit user action, never auto-lowered by CLI mode flapping. The verdict protocol is taught by a hidden **primer** (`src/grok-primer.ts`) — it tells grok to ignore the bogus `exit_plan_mode` result and read `[Plan approved]`/`[Plan rejected]`/`[Plan cancelled]` (optionally + a comment) from the follow-up message. **The primer fires eagerly + non-blocking** as its own hidden turn the moment a session goes live — on new AND restored sessions, and after `/compact` — *not* in front of the user's first prompt and *not* at composer-disabling cost (`ensurePrimed` in `sidebar.ts`, kicked off from `startSession`'s success path). It returns a reused `session.primingPromise` (`src/session.ts`) so a racing first send awaits the *same* in-flight primer (grok runs one turn at a time) and is released the instant the silent primer acks; the user can type and send straight away — their bubble shows immediately (a "Grokking…" indicator stands in until grok produces content) while the real prompt is held behind the primer in code. On restore the primer is *re-sent* on first go-live rather than trusted from replayed history (a `/compact` can drop it). The primer's silent turn is hidden by a session-level `suppressContent` flag checked in `emit` against `SUPPRESS_TYPES` (which deliberately **excludes** `userMessage`/`agentStart` so a user send that races the background primer still paints its own bubble + Grokking indicator). **Primer v4** (`PRIMER_VERSION`/`PRIMER_MARKER`) is deliberately minimal: grok-build is agentic, and the old v3 primer's "## Grok Build VS Code extension … open source repo, issues: <URL>" paragraph + "Acknowledge briefly" line were tempting grok into a 15–40s pre-turn exploration of the workspace (one capture: 17.7s reading files + searching 114 files) before the user's message even ran — the plan-protocol text itself never did. v4 keeps only the protocol, drops the product paragraph + URL, and adds an explicit *do not use any tools / do not read files / do not search the workspace / do not take any action* constraint ending in "Reply with exactly: ok". The pure `isPrimerText()` (version-agnostic `PRIMER_PATTERN`) detects the primer when grok replays it so the bubble is hidden + not counted toward plan positions. For the full pedagogical course with diagrams and hands-on guidance, see `research/understanding-plan-mode.md`.

The setup card / quick-settings popover remain WP7. See `docs/plans/claude-code-backend.md` and `research/claude-code-backend.md`.

## Known limits

- **Cross-CLI peer agent (opt-in)** — `grok.peerAgent.enabled` (default **off**) injects a loopback **HTTP** MCP server into ACP `session/new`/`load` exposing `run_peer_agent`, and registers **Grokbit: Run on other agent…**. Both Grok and Claude ACP advertise `mcpCapabilities: {http,sse}` only (no stdio) — see `research/peer-agent-mcp.md` and ADR 0005. Peer nesting depth is 1 (child sessions omit the MCP). v1 headless peers **auto-allow** permissions (no parent-tab permission routing yet). This is **live nested delegation**, not a substitute for suite disk artifacts under `.grokbit/plans/`, and it does **not** make Grok `.rhai` / Claude `.js` User Workflows interchangeable.
- **Grokbit Workflows default scope is suite + User Workflows only** — skills, agents, and CLI commands are filtered unless `grok.actionsScope` is `all` (`CAPABILITY_VISIBLE_KINDS = ["grokbit","workflow"]`). User Workflows are **backend-native** (Grok Rhai vs Claude JS); there is no cross-format transpile. Discovery and `/` autocomplete for skills/commands are unchanged.
- **A workspace fork of a suite skill is invisible in Actions** — `applySuiteKind` deliberately leaves a repo-authored `grokbit-plan` as `kind: "skill"` so it is not badged as Grokbit's own (`src/skill-suite.ts`); that item now falls outside `CAPABILITY_VISIBLE_KINDS` and does not render.
- **Dual-stack / dual-hook collision** — this repo (and any workspace) may have **both** `.grok/hooks/` (Grok Python harness) and Claude hooks (`.claude/hooks/` or a `hooks` key in `.claude/settings.json`). Under folder trust, Grok can load **both** stacks, so a turn may run two Stop gates, two change markers, and double unit-test runs. Prefer one stack per session type; the extension logs a soft dual-stack warning on activation / hook install (`detectDualHookStacks` in `src/hook-suite.ts`) and never auto-renames Claude agents. Grok hooks provision is **opt-in** (`grok.hooks.provision` default `off`; command **Grokbit: Install workspace harness hooks**); after install run `/hooks-trust`. Hooks are a **backstop only**, not accuracy protocol.
- The launcher's development-token figure (§ Token surfaces) has three accepted limits, all deliberate. **The grok bucket under-reports and cannot be improved** — grok persists no per-turn record on disk (verified: `events.jsonl` carries only `first_token` latency markers, `chat_history.jsonl` carries no `usage` object), so its `contextTokensUsed + totalTokensBeforeCompaction` proxy is a lower bound; it is tagged `accounting: "context-proxy"` in the ledger rather than silently mixed with Claude's exact billed figures. **Coverage is only as complete as the machines that have run the aggregator** (today: one maintainer's laptop) and Claude Code prunes transcripts over time — the per-session `max` merge preserves what has been seen, but cannot recover what aged out before the first run. **The figure is stale between releases** by up to one release, since it's baked in at package time; the tooltip's *as of \<date\>* is the honest disclosure, and closing that gap at runtime is exactly the rejected design (see `docs/adr/0003-development-token-ledger.md`). A failed regeneration is also silent by design — regeneration is non-fatal so it can never block a release, and the previous constant just ships again
- Subagent delegation cards are deferred — grok 0.2.x doesn't emit `spawn_subagent` over ACP (it backgrounds a process + polls), so the classifier rarely fires; even when it does, child tool calls aren't nested (no inspector)
- Generated media is served via `asWebviewUri` (streamed from disk) when it lives under the grok-home `localResourceRoot`; files outside that fall back to a base64 `data:` URI
- No worktree UI
- The inline edit diff is preview-only (proposed old vs. new text, not disk at preview time); the write happens via `fs/write_text_file` after approval
- The launcher view is single-homed to the left activity bar (`viewsContainers.activitybar` only — declaring `secondarySideBar` too is invalid below VS Code 1.106 and misplaces the view, esp. in Cursor); user relocates to the secondary side bar via *Move To → Secondary Side Bar*, which persists
- Live-process count is soft-bounded only (one-time warning past 8 live tabs; nothing is killed) — the old idle/LRU reaper is deliberately retired in favor of tab visibility + lazy start
- `retainContextWhenHidden:false` is a deliberate dial: a hidden tab's webview is torn down and rebuilt on reveal (replay covers it); flipping it to `true` would break the `ready`-driven replay lifecycle
- Installing the Claude Code adapter (`installClaudeAdapter`) is an asynchronous ~120 MB npm install (`execFileAsync` + progress notification); cancel is best-effort if offered by the progress UI
- Claude's on-disk token usage is a per-turn `message.usage` proxy, not an authoritative context measure like grok's `signals.json` — it reflects the last completed turn, so a resumed tab's donut can lag reality until the next turn lands
- Claude has a **client-side fs/terminal plan-mode backstop** (`clientPlanGate: true`) matching Grok; **permission pre-reject** and **plan-restore override** stay grok-only (`clientPlanPermissionReject: false` for Claude) so native Claude plan UX is not clobbered.
- An approved permission is **path/command-bound** when the payload carries an extractable path or command (`src/permission-bind.ts`): a later write/command to a different target is refused while scoped grants remain. **Allow once** Write grants that include preview `content` also bind a content digest — same-path body bait-and-switch is refused. **Allow always** / Auto-accept and Edit-only permissions (no full `content`) stay path-scoped for content. Grants with no extractable path do not invent security.
- `updateGrokCliOnDemand` tears down **Grok** sessions only; Claude tabs keep their live process across a Grok CLI update.
- Permission binding is path/command-scoped by default; content digests apply to non-durable Write previews only (see above). Claude's previewed diff is often *synthesized* from `rawInput` and is labelled "Preview from agent input" in the card when no structured ACP diff was available.
- The capability browser does **not** enumerate MCP servers (grok's live in `config.toml` under `[mcp_servers.<name>]`, a TOML format this extension has no parser for; Claude's is a different format entirely), personas (`.grok/personas/*.toml`, grok-only), or plugins (`~/.grok/marketplace-cache/…`, `~/.claude/plugins/…` — two different marketplace layouts plus enable/disable state). **User Workflows are shipped** as `CapabilityKind: "workflow"` — Grok `.grok/workflows/*.rhai` and Claude `.claude/workflows/*.js` are discovered on disk (formats are **not** interchangeable); the Grok **Create Workflow** tile opens a vanilla form+canvas builder (ADR 0004) that auto-sends `/create-workflow` and returns the proposal into the builder. Default Actions UI still filters to suite + workflows unless `grok.actionsScope` is `all`. grok's `config.toml` **TOML** vendor-skill opt-out (`[compat.claude] skills = false`) is not honored (no TOML parser) — only the plain-string **env-var** form (`GROK_CLAUDE_SKILLS_ENABLED`/`GROK_CURSOR_SKILLS_ENABLED` set to a falsey value) is.
- There is **no filesystem watcher** over the capability roots — discovery is request-driven, so a skill added mid-session appears only after a `Refresh` click, a tab switch, or a `commandsUpdate`. This matters most for a skill *the agent itself* writes (`fs/write_text_file` fires no `onDidSaveTextDocument`, so nothing else could catch it either). Deliberate: a persistent OS-level watcher on `~/.grok/**` and `~/.claude/**` needs per-backend root→glob translation plus disposal wiring, for a panel that's only on screen on an empty tab. Revisit if the manual refresh proves insufficient in practice.
- Capability discovery scans the **workspace root and home tier only** — not every intermediate directory between cwd and repo root (grok's `08-skills.md` says the CLI itself does). In VS Code workspace root ≈ cwd ≈ repo root, so this is near-invisible in practice. Namespaced command subdirectories (`.claude/commands/frontend/x.md` → `/frontend:x`) are likewise not discovered — real for Claude Code, unverified for grok, and untested against a real layout.
- The activity-bar launcher fully re-renders its whole Recent list (`renderRows()` clears and rebuilds `#launcher-list` from scratch, up to 500 rows × 2 inline SVGs each) on **every** host-pushed `sessions` message, and `broadcastSessionsList()` pushes one on 14+ call sites (send, rename, delete, tab open/close, …). The sticky-window guard (see § History pagination) stops a scrolled-in window from visibly *shrinking*, but it doesn't stop the full DOM rebuild underneath — a busy window near the render ceiling repaints hundreds of rows on nearly every action. Known, deliberately deferred (a real fix — diffing/patching rows instead of clear-and-rebuild — is a bigger perf change than a fix-batch should carry); revisit if it's ever a measured, user-visible stall rather than a theoretical cost.

## Cross-platform notes

- `terminal-manager.ts` uses `spawn(cmd, { shell: true })` so Node picks `cmd.exe` on Windows, `/bin/sh` elsewhere. Don't hardcode shell paths.
- `cli-locator.ts` reads `HOME` / `USERPROFILE` env vars first (testability), falls back to `os.homedir()`. Uses `where` on Windows, `command -v` elsewhere. Checks `.cmd`/`.exe`/`.bat` extensions on Windows.
- Tests use `node -e "..."` everywhere, so commands are deterministic across platforms — don't add `pwd`, `awk`, `sleep`, `true`, etc.

## Publishing

**Release procedure — ALWAYS tag + create a GitHub Release (with the `.vsix` attached) on a release push to `main`** (standing convention; mirrors the `v1.0.0…` tag history + GitHub Releases):

**The whole procedure below (steps 2–5) is scripted** — after bumping the version + writing the changelog section (step 1, user-initiated), just run:

```bash
pwsh scripts\release.ps1        # Windows (native) — what we use here
./scripts/release.sh            # macOS / Linux / WSL
```

It reads the version from `package.json`, runs the gate, builds the vsix, commits the working tree (`-MessageFile`/`-Message` override the default `Release vX.Y.Z`), pushes `main`, creates the annotated tag, and runs `gh release create` **with the vsix attached** — extracting the matching `## X.Y.Z` changelog section as the release notes. `-DryRun`/`--dry-run` previews; `-NoTest`/`--no-test` skips the gate. It refuses to run off `main` or when the tag already exists (i.e. the version wasn't bumped). The script does **not** call `vsce`/`ovsx`, and there is **no publish workflow** (`.github/workflows/` is just `ci.yml`) — so the GitHub Release does **not** auto-publish to the Marketplace. Marketplace publish is part of **`npm run rebuild` / `/rebuild`** (step 4 of the rebuild contract; needs `VSCE_PAT` or `vsce login`). Open VSX and standalone `npm run publish` remain separate when needed.

What the script encodes, step by step:

1. Bump `version` in `package.json` (user-initiated) and add the dated section to `CHANGELOG.md`. As part of this pass, **review the release-facing docs for staleness against what actually ships** — this review is a required step, not optional:
   - `README.md` — features / screenshots / install matrix.
   - `TESTS.md` — test plan vs. what actually ships.
   - `CLAUDE.md` — the project map (§ Module map, § ACP surfaces, § Known limits, the test-count floor): does it still describe the current architecture? It deliberately **doesn't** hardcode the version (it points to the changelog), so it needs no version edit — but its prose can go stale as behavior changes.
   - `docs/architecture.md` — the architecture doc: keep it in sync with new modules / event flows / surfaces.
   - `package.json` itself — description, `engines`, `categories`, `contributes`.
   - `docs/metrics/token-usage.json` + `src/token-metrics.ts` — the generated development-token ledger and its constant (§ Token surfaces). Run `npm run metrics:tokens` and commit the result so the release ships a current figure and the number's movement is visible in the release diff. `/rebuild` also refreshes these (non-fatally), so verify they actually regenerated rather than assuming.

   Keep `CHANGELOG.md` entries **terse** (1–3 bullets per release under Added/Changed/Fixed; deep detail belongs in commits / `research/`, not the changelog); releases before the current minor live in `docs/CHANGELOG-ARCHIVE.md` (linked from the foot of `CHANGELOG.md`).
2. `npm test` (1336-test floor, all green) + `tsc -p . --noEmit` clean, **and `npm run test:live` against real grok — mandatory, run without asking** (the `release.*` scripts don't run it, so run it by hand before invoking them).
3. Commit + push to `main` (direct-to-main, no feature branches).
4. **Annotated git tag** `vX.Y.Z` at the release commit → `git tag -a vX.Y.Z -m "Release vX.Y.Z"` → `git push origin vX.Y.Z`.
5. **GitHub Release** for that tag → `gh release create vX.Y.Z --title "Release vX.Y.Z" --notes-file <notes> <vsix>` (notes = the new changelog section(s); include any earlier version that was bumped but never released). **Always attach the built `grokbit-X.Y.Z.vsix` as a release asset** so the exact installable build is downloadable from the release.
6. **Marketplace publish** — default path is **`npm run rebuild` / `/rebuild`** (publishes the just-built vsix). Standalone: `npm run publish`. The `Grokbit` publisher must be registered + authenticated (`VSCE_PAT` or `npx @vscode/vsce login Grokbit`); publishing ≠ tagging.

Don't skip the tag/release (or the vsix asset) on a release push. (A pure mid-dev version bump that isn't a release — e.g. the unreleased v1.3.0 voice iteration — is the only exception.)

## Repo conventions

- **Work on `main`, synced to `origin/main`.** `main` is the only working line — start every task from `main` fast-forwarded to `origin/main`. The `dev` branch is **abandoned** (stale far behind `main`); do **not** develop on it. If the working tree is on `dev`, or `main` is behind `origin/main`, switch to `main` and `git reset --hard origin/main` before doing anything else (the published version lives on `main` — a stale checkout will look many versions behind and misnumber the changelog).
- Direct-to-`main`, no feature branches
- **Do not commit or push outside the rebuild/release paths.** Day-to-day agent work leaves the tree uncommitted unless the user explicitly asks to commit. Exceptions that **do** commit and push: a full **`npm run rebuild` / `/rebuild`** (after Marketplace publish succeeds) and **`scripts/release.*`**. Local-only rebuild (`--no-publish`) does **not** commit or push.
- Commits explain the *why*, not the *what*
- Don't introduce abstractions speculatively
- Don't add comments that explain what well-named code already says
- 1336 tests is the floor — every PR should keep that green. All tests are grok-free (and claude-free — never spawn either binary); grok-dependent probes live in `research/*.cjs` and are run manually, never by `npm test` or CI
- **Rebuild = bump version + package + reinstall + Marketplace publish + commit/push (all five, always).** When the user asks to **rebuild**, agents **must**:
  1. **Increment** `package.json` CalVer (`scripts/bump_extension_version.py` → `YYYY.M.N`) — never ship the same version number again.
  2. **Package** a fresh `.vsix` (`npm run package` clears older `grokbit-*.vsix` first).
  3. **Reinstall** into VS Code (`code --install-extension <vsix> --force`) — **package-only is not a rebuild**; the installed extension must be updated too.
  4. **Publish** the same vsix to the VS Code Marketplace (`npx @vscode/vsce publish --packagePath <vsix>`) unless the user asked for local-only / passed `--no-publish`. Needs `VSCE_PAT` or a prior `vsce login Grokbit`.
  5. **Commit + push** the working tree after publish succeeds (`git add -A` → `git commit -m "Rebuild vX.Y.Z"` if dirty → `git push origin <current-branch>`). Skipped with `--no-publish` or when installing an explicit vsix path only. Does **not** create a tag or GitHub Release.
  **Preferred path:** `npm run rebuild` (or `/rebuild` in chat) — same as `pwsh scripts\install.ps1` (Windows) / `./scripts/install.sh` (macOS/Linux/WSL); each does bump → package → install → publish → commit+push by default. Local-only: `npm run rebuild -- --no-publish` (skips publish and git). Passing an explicit prebuilt vsix path installs that file only (no bump/publish/commit) — fine for installing a known artifact, not a rebuild. If not using the install scripts, still run the full contract yourself. Add/update the matching `CHANGELOG.md` section when the rebuild ships behavior changes. **Package last among edits:** the vsix bundles `README.md` and `docs/screenshots/**` (`.vscodeignore` excludes `CLAUDE.md`, `TESTS.md`, `AGENTS.md` and the rest of `docs/**`), and it bundles `out/**/*.js` — including the **generated** `out/token-metrics.js` — so finish *all* doc + code edits, and any `npm run metrics:tokens` refresh, **before** the final rebuild, or the installed build ships a stale snapshot. Mid-task rebuild then more edits → rebuild again. This is independent of the agentic-template `VERSION` file (commit metrics). **Release tag + GitHub Release remain user-initiated** (or the release scripts when releasing) — Marketplace publish and the rebuild commit/push are part of `/rebuild`, not of `release.*`.
- **Sign GitHub comments.** Every GitHub issue/PR comment posted on the user's behalf ends with a signature on its own final line (italic). Pick by whether Israel actually reviewed the text before it was posted: if he reviewed it, use `_Written with an agent, reviewed by Israel_`; if the agent posted it without his review, use `_Written by Israel's agent_`. Only claim review when it actually happened.
