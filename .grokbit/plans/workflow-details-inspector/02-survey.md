## Workflow file formats

**What exists on disk in this repo:** `.grok/workflows/post-change-testing-protocol.md` (read in full) — a plain narrative Markdown file (26 lines), numbered steps referencing other skill files, with no `let meta = #{...}` block, no `agent()` calls, no Rhai syntax at all. Per `.grokbit/plans/user-workflows-tile/03-design.md:61` ("Template `.md` under `.grok/workflows`" → disposition **LEAVE**, "not Rhai"), this file is explicitly *not* scanned by the `flat-rhai` layout (`src/capabilities.ts:805-808` only accepts `name.toLowerCase().endsWith(".rhai")`), so it is invisible to `scanCapabilityRoots` regardless of any Details feature. There is a same-named `.bak-agentic-20260723-175425` backup file alongside it (not opened — a backup, not a workflow). Both `.grok/` and `.claude/` are gitignored (`.gitignore:17-18`), so neither directory's contents are committed/shareable state.

**What the parsers actually recognize (confirmed against real test fixtures, `test/capabilities.test.ts:790-809`):**

- **Grok Rhai head shape:**
  ```
  let meta = #{
      name: "review-changes",
      description: "Review a diff across dimensions",
      phases: [ #{ title: "Review" } ],
  };
  phase("Review");
  ```
  `parseRhaiWorkflowMeta` (`src/capabilities.ts:468-493`) locates `let meta = #{` via regex, brace-balances to find the matching `}` (handles nesting, not quote-aware inside strings beyond `extractMetaStringField`'s own string-literal regex), and hands the whole matched block to `extractMetaStringField` (`src/capabilities.ts:448-462`) once for `"name"` and once for `"description"`. The `phases: [...]` array in the fixture is present in the source text but **never read** — no code path walks it.

- **Claude JS head shape:**
  ```
  export const meta = {
    name: 'spot-review-fanout',
    description: 'Review every rendered spot across four lenses',
    whenToUse: 'After a batch of spots renders. Budget accordingly.',
    phases: [ { title: 'Review' } ],
  };
  ```
  `parseClaudeWorkflowMeta` (`src/capabilities.ts:499-544`) does a hand-rolled brace/quote-aware scan (tracks `inStr`/`escape` state so a `}` inside a string literal doesn't end the block early — more careful than the Rhai parser, which has no such string-awareness for its own top-level brace count) to find the `export const meta = {...}` object, then extracts `name` and `description` (falling back to `whenToUse`/`when_to_use`). Same limitation: `phases` is present but unread.

- **`extractMetaStringField`** (`src/capabilities.ts:448-462`) is a single shared regex-based value extractor used by both parsers: matches `key: "value"` / `key: 'value'` / `` key: `value` `` (bare `key = "value"` too), handles escaped quotes/newlines inside double-quoted strings, trims and returns `undefined` for an empty match. It extracts exactly one scalar value per call — it has no concept of arrays, nested objects, or repeated `agent(...)` calls; `capabilityFromWorkflowFile` (`src/capabilities.ts:568-585`) calls the format-specific meta parser exactly once per file and builds one `CapabilityItem` from the two returned scalars (`name`, `description`).

- **Read bound:** both parsers only ever see `fs.readHead(filePath, headBytes)` (`src/capabilities.ts:839`, default `headBytes = CAPABILITY_HEAD_BYTES = 8 * 1024`, `src/capabilities.ts:182`) — the first 8KB of the file. A workflow script with several phases and many `agent()` calls (the kind of script the intent wants to summarize) is plausibly larger than 8KB; today's scan would silently truncate mid-file for such a script, and neither parser reports truncation.

- **No literal Rhai `agent(prompt, opts)` call syntax was found anywhere in the repository** (searched `agent\(prompt`, `fn main`, `phase\(` across `*.rhai` — no files; across all files for the meta-block patterns — only test fixtures and plan documents, listed below, none showing a full script body with agent-call syntax). The intent document's premise that scripts contain agent calls with settings (model/effort/schema) could not be corroborated against a real file in this repo; it rests on the plan documents' prose description of the target format, not an observed example.

## Payload & message plumbing

**`capabilities` message (host → webview), posted by `listCapabilities` (`src/sidebar.ts:3419-3499`):**
```
{ type: "capabilities", backend, groups: CapabilityGroup[], scannedRoots, truncated,
  mcpServerCount, actionsScope }
```
or, on scan failure: `{ type: "capabilities", backend, groups: [], scannedRoots: 0, truncated: false, error }`. Sent via `this.postTo(session, …)` (`src/sidebar.ts:3479`, `:3490`) — **not** `emit` — so it is never buffered into `Session.buffer` and is dropped if the panel isn't ready (matches the documented `postTo` contract for "derived, refreshable state" in `src/panel-router.ts:9-17`). Each `CapabilityGroup` item carries the full `CapabilityItem` shape (`src/capabilities.ts:45-72`) — for a workflow item today that's `{kind:"workflow", name, description, invoke, path, source, origin:"disk"}` and nothing else (no `hasDetail`/`detailPath`, since only `applySuiteKind`+`attachSuiteHowItWorks` stamp those and only for `kind:"grokbit"`).

**`getCapabilityDetail` / `capabilityDetail` (already-shipped suite-only detail lazy-load):**
- Webview → host: `{ type: "getCapabilityDetail", name: string }` — union member `src/sidebar.ts:198`, dispatched at `src/sidebar.ts:3254-3255` to `this.getCapabilityDetail(session, name)`.
- Handler (`src/sidebar.ts:3505-3532`): resolves `name` through `resolveSuiteHowItWorksPath` (`src/skill-suite.ts:227-235`), which **rejects any name not in `SUITE_SKILL_NAMES`** (`src/skill-suite.ts:232-233`) — so this endpoint cannot read an arbitrary path today, only the 6 hardcoded suite skill names, and only their `references/how-it-works.md` under the extension's own bundle root (`suiteHowItWorksPath`, `src/skill-suite.ts:174-176`). Reads via `fs.statSync`/`fs.readFileSync`, capped at `HOW_IT_WORKS_MAX_BYTES = 64 * 1024` (`src/skill-suite.ts:168`) — a full read with a size ceiling, a materially different pattern from the 8KB *head-only* scan read used for meta parsing.
- Host → webview: `{ type: "capabilityDetail", name, markdown, path }` or `{ type: "capabilityDetail", name, error }` (`error` ∈ `"not-a-suite-skill" | "not-found" | "too-large" | "read-failed"`), also via `postTo` (`src/sidebar.ts:3509`, `:3515`, `:3519`, `:3523-3528`, `:3530`).
- Webview render (`media/chat.js:6096-6119`): looks up `state.pendingCapabilityDetail` (stashed at click time, `media/chat.js:881`), renders the markdown through the **existing safe markdown pipeline** `renderMarkdown(md)` (`media/chat.js:6114`, wrapped in try/catch falling back to `textContent`) — never raw `innerHTML` of untrusted text.

**`openFile` (webview → host, existing, read-only):** `{ type: "openFile", path: string }` — union member `src/sidebar.ts:161`, handler `src/sidebar.ts:2976-3012`. Validates the path (`isUsableFilePath`/`parseFileRef`), resolves relative-to-workspace-root, and either opens the file in a text editor (optionally with a line-range selection) or hands it to `vscode.env.openExternal` for a business-doc binary. **It never writes.** Used today by the workflow Details' "Open in editor" secondary button (`media/chat.js:895-905`, posts `{type:"openFile", path: item.detailPath}`).

**Write-path conclusion:** the only webview-reachable file mutation channel in the whole message union (`src/sidebar.ts:145-199`) is the math/diagram `exportExpr` flow (renders SVG/PNG to a user-chosen save target, `src/sidebar.ts:1755`, `:1786`, `:1789` — all inside the `exportExpr` handler, unrelated to workflow files). A dedicated webview→host "edit this workflow file" write channel **DOES NOT EXIST**.
