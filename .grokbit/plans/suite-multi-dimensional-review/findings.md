## Team architecture (summary)

The suite's team design is genuinely strong on verification discipline — context-isolated adversarial review, files-only role communication, capped loops with per-phase cap semantics, verify-or-revert, and an honest Orchestrator — but it is a QA-and-safety organization, not a complete engineering team. Nobody on the 18-role roster ever reviews code quality (the implement Code Reviewer explicitly disclaims it at grokbit-implement/references/roles.md:78), nobody owns durable tests for NEW behavior, nobody owns branch/PR/CI strategy (commits land directly on the checked-out branch), security review exists only after code is written, and there is no fast path — a typo fix draws the full ~25-invocation pipeline, which for the vibe-coder audience is exactly the retention failure the suite's own 3-question-cap rationale (grokbit-plan/references/loops.md:28) warns about but never applies to itself. The waterfall shape is better-mitigated than most (per-task verify commands, pre-implementation baseline, contract-defined backward edges), but three end-loading problems are unmitigated: security, visual feedback, and regression detection all arrive only at test time, and the test→implement hand-back can only append a task, so a design-shaped finding discovered at test has no route back to plan short of accumulating 3 unrelated deviations.

## Cross-skill audit (summary)

The suite's intra-skill machinery is genuinely strong — caps, precise revert semantics, verdict vocabularies, and the replan contract are specified with unusual care and are internally consistent — but the seams between skills are where it falls short of a world-class process. The two inter-phase cycles (implement<->test hand-back and implement->plan replan) are unbounded by design: hand-backs are explicitly exempted from the only counter and the replan counter resets each iteration, with no depth-aware escalation to the human. Several declared handoffs have no counterpart on the other side: the security repair path has no intake, failed done-criteria trigger neither DO NOT SHIP nor Step 7, nobody is assigned to tick the approval checkbox Implement requires, and Document's context digests and emit_at hooks are write-only/never-fired. Two state-handling holes can strand or corrupt user work: the dirty-tree stash is created and never restored anywhere, and baseline mode commits before any clean-tree discipline exists. Verdict/mode/disposition vocabularies (SHIP triad, INTENDED/REGRESSION/UNKNOWN, IN_SCOPE triad, REPLACE/DEPRECATE/COEXIST/LEAVE) are otherwise plumbed consistently, and diagrams agree with prose on pipeline ordering except one ambiguous T3 hand-back edge.

## Scripts/template audit (summary)

The template layer is the strong half of this suite: every field and section the five SKILL.md files and their loops.md name is present in the corresponding asset template, including the subtle ones (plan.template.md's removes/baseline/state-after and approval checkbox, results.template.md's Reduced-mode and Baseline-retirement sections, deviations.template.md's waiver-vs-count distinction), and no prose-vs-template mismatch was found. The executable layer is weaker than its prose: most Step 5 and Staleness claims are genuinely implemented (anchor checking, citation existence, exit-code 3 for listed-not-verified, --execute refusal gate, no-provenance flagging, --ci), but the highest-severity problems are process-level — Loop D1's "counts only if executed" rule is unsatisfiable on the declared audience's machine and contradicts its own "zero BLOCKER" exit criterion, leaving an agent to choose between a false-clean ship, a permanent block, or self-passing the shell-execution bypass flag; and the shipped Claude Code hook hardcodes an install path the extension's real provisioning never creates, so the promised advisory drift check silently never runs. Below that sit real correctness defects: bash fences executed via cmd.exe//bin/sh under --execute, three classes of false-positive link BLOCKERs that hard-block documents under D1, and unresolvable paths that never fail the exit code despite loops.md declaring them BLOCKER-class. The __pycache__ bytecode is not a vsix or git defect (both ignore files exclude it) but exposes an unfiltered provisioning copy and absent payload-hygiene checks. The deepest gap for a world-class claim is that the suite's only executable enforcement tools ship with zero tests, in a repo whose own standard is a 1336-test floor.

- **grokbit-plan** — No security or privacy thinking at design time: the design template's risk surface is the unhappy-path table (network failure, empty state, concurrent edit, permission denied) and a migration section — no threat consideration, authZ-change review, secrets handling, or input-validation requirement. The suite defers all security to grokbit-test's post-implementation pass, which is exactly when design-level security flaws are most expensive to fix. A world-class team does security review at the design gate.
- **grokbit-plan** — No repo-state anchoring or staleness contract: 02-survey.md citations are not pinned to a git SHA and nothing detects the repository changing between survey, approval, and implement start. A plan approved Friday against Monday's very different tree presents the same confident citations. World-class: record HEAD at survey time and have implement's preflight diff against it.
- **grokbit-plan** — No plan-time smoke-check that the verify harness itself exists: Loop 4 validates verify: commands purely by inspection against the survey's conventions section. One cheap dry-run (does package.json actually have a test script? does the named runner exist?) would catch the most common downstream deviation class ('a verify command that could not execute in this environment' is an enumerated I5 deviation type) before the gate instead of after three of them force a replan.
- **grokbit-plan** — No quality bar on rollbacks for stateful changes: the checklist requires only 'Has a rollback', and the template's example is 'git revert <commit>' — which does not un-apply a database migration, un-send an email, or un-publish a package. The design template asks 'Reversible:' for migrations but nothing forces the corresponding task's rollback: field to be a real down-migration. A world-class plan distinguishes code rollback from state rollback per task.
- **grokbit-plan** — No non-functional requirements capture: the intent template's done-criteria are purely functional/observable; there is no prompt for performance budgets, accessibility, i18n, or observability (logging/metrics for the new code path), so the Reviewer has no basis to flag their absence and the plan cannot fail for lacking them.
- **grokbit-plan** — No rollout/exposure planning for risky changes: no concept of feature flags, staged enablement, or kill switches even when the design's own migration section admits a mixed-version window — the plan goes from approval to full deployment of behavior with no intermediate exposure state.
- **grokbit-plan** — No post-approval integrity protection on plan.md: the human's approval checkbox (plan.template.md:85) is a mutable markdown line with no snapshot or hash of what was approved; nothing distinguishes the approved text from later agent edits, so 'the human approved this plan' is unverifiable after the fact.
- **grokbit-plan** — No estimation or risk-ranking of tasks: blast radius is a single header line (N files, N deps, schema y/n); individual tasks carry no risk or size signal beyond the ~200-line guide, so the human at the gate cannot see which of twelve tasks is the dangerous one — a world-class gate presentation leads with it.
- **grokbit-implement** — No code-quality review exists anywhere in the phase: the Code Reviewer is explicitly scope-only ('You are not reviewing code quality in general', roles.md:78), so logic errors, missing edge cases, and poor error handling that happen to pass the single verify command ship unreviewed — a world-class team reviews the change itself, not just its boundary.
- **grokbit-implement** — No branch isolation or whole-plan abandonment procedure: every task commits directly to the user's current branch, so a DO NOT SHIP verdict or an abandoned session leaves N unshippable commits on (typically) main with no defined unwind beyond per-task `git revert` — a world-class team implements on a branch where abandonment is deleting it.
- **grokbit-implement** — No safety screening of plan-authored verify commands before execution: Implement runs `verify:` verbatim up to three times; a destructive command (rm -rf, git clean, db reset) that survived plan approval by a non-expert executes unchecked — a world-class process lints or sandboxes commands it did not write.
- **grokbit-implement** — Dependency-gate trigger coverage is a hardcoded three-command list ('Any npm install, pip install, cargo add', SKILL.md:75): yarn/pnpm/bun/poetry/uv/go get are ungated, and editing package.json directly followed by a bare `npm install` bypasses the gate entirely; the gate also never mandates --ignore-scripts or post-install lockfile pinning, so an approved package's install scripts still run arbitrary code.
- **grokbit-implement** — The progress.md `Cost` column demands per-task dollar figures ($0.12, $0.48 in the template) that neither host CLI exposes to the agent — the skill's own ethos is 'record actual observed values rather than expectations,' yet this field can only be fabricated; a world-class process either wires real cost telemetry or drops the column.
- **grokbit-implement** — No concurrency protocol for artifacts: two sessions on the same slug (or two slugs sharing the single-slot .grokbit/handoff.md, which Step 6 acknowledges is last-writer-wins) clobber each other's progress.md/deviations.md with no lock, lease, or even a 'check for a live session' step.
- **grokbit-implement** — No replan-count ceiling: Loop I5 can fire repeatedly (replan-1, replan-2, ...) with no rule that after N failed replans the correct action is human takeover rather than another Survey pass — the human approval gate is the only brake, same weakness as the hand-back cycle.
- **grokbit-test** — No flaky-test or quarantine policy anywhere: nothing distinguishes 'red because broken' from 'red because flaky' — no rerun rule, no stability check at baseline commit time, no quarantine list carried between sessions.
- **grokbit-test** — No test-adequacy measure for NEW code: the phase checks stated done-criteria and old behavior (baseline replay), but new logic paths that have neither a criterion nor a pre-existing behavior are never required to be exercised — no changed-line coverage, branch coverage, or mutation check on the diff.
- **grokbit-test** — No rollback rehearsal: grokbit-plan mandates a rollback per task and release-readiness.template.md asks 'Reversible: yes', but nothing ever executes a rollback or a down-migration to prove reversibility — a world-class release-readiness check exercises the escape hatch, not just asserts it.
- **grokbit-test** — No performance regression check beyond bundle/image size delta: no latency, memory, query-count, or startup-time comparison against baseline, even though the baseline phase is the natural place to capture those numbers.
- **grokbit-test** — No accessibility pass in visual QA: the Frontend QA checklist (render, clip, overlap, states) omits contrast, focus order, keyboard reachability, and ARIA — standard items on a world-class FE QA checklist and cheap to add headlessly (e.g., axe-core).
- **grokbit-test** — No global cap or escalation rule on test↔implement hand-back round trips: each round has a one-line human approval, but a vibe coder will rubber-stamp; a world-class process escalates to replan (grokbit-plan) after N failed verify rounds the way implement's own 3-deviation rule escalates.
- **grokbit-test** — No test-data/fixture strategy for baseline capture: 'exercise the real code path' is silent on auth, seeded databases, and external services beyond the NOT CAPTURED escape hatch — a world-class characterization effort defines how to stand up representative state.
- **grokbit-test** — No artifact-hygiene rule for the skill's own outputs: screenshots and verbatim 'observed output' captures can embed PII, tokens, or secrets rendered on screen into .grokbit/plans/<slug>/test/, which the Security step never scans because it scans the change diff, not the test artifacts.
- **grokbit-test** — No cross-browser/device dimension in visual verification: one headless engine at two widths is assumed sufficient; no statement of the limit, so a vibe coder reads PASS as 'works everywhere'.
